# 03 核心模块说明

> 同步日期：2026-05-23  
> 分析范围：`novel_system/`、`templates/`、`static/`、`start_server.py`。  
> 说明：本文从当前代码入口、依赖和调用关系出发描述模块；无法从代码直接确认的内容标注“待确认”。

## 主链路概览

```text
start_server.py
  -> novel_system.api:app
     -> create_app()
        -> AppConfig.load()
        -> create_service()
           -> GraphService()
              -> NovelSystemService
                 -> QAServiceMixin
                 -> ContinuationServiceMixin
                 -> IndexingServiceMixin
                 -> StatsServiceMixin
                 -> NovelSystemBase

Dashboard:
templates/dashboard.html + static/app.js
  -> HTTP API
     -> api.py route
        -> service method
           -> repo / planner / retrieval / validator / llm / graph / tracing
```

当前真实服务实例不是纯 `NovelSystemService`，而是 `create_service()` 返回的 `GraphService()`。`GraphService` 继承 `NovelSystemService`，因此 API 路由调用到的服务方法会经过该继承层。

## 启动入口和 Web 层

### `start_server.py`

- 入口：命令行执行 `python start_server.py` 或 `conda run -n chaishu python start_server.py`。
- 依赖：导入 `novel_system.api:app`，使用 `uvicorn.run()` 启动 `0.0.0.0:8000`。
- 调用关系：不直接创建服务，服务创建发生在导入 `novel_system.api` 时。
- 边界不清：AGENTS 和部分文档提到 `python -m novel_system.api`，但当前 `api.py` 没有 `if __name__ == "__main__"` 启动逻辑。待确认正式启动命令是否应统一为 `start_server.py`。

### `novel_system/api.py`

- 入口：`create_app()` 和模块级 `app = create_app()`。
- 依赖：`FastAPI`、`CORSMiddleware`、`StaticFiles`、`Jinja2Templates`、`AppConfig`、`create_service()`、`AskRequest`、`ContinueRequest`、`CanonUpdateRequest`、`Scope`。
- 被调用方：`start_server.py` 导入 `app`；测试或 ASGI 服务也可直接使用 `novel_system.api:app`。
- 调用谁：路由函数调用 `service.list_books()`、`service.index_book()`、`service.ask()`、`service.continue_story()`、`service.get_interactive_graph()`、`service.get_dashboard_data()` 等。
- 当前职责：应用工厂、路由注册、文件上传处理、book_id 编码/解码、静态资源挂载、Dashboard 模板渲染。
- 边界不清：路由层包含文件落盘、上传文件名修复、book_id 生成等业务前置逻辑；页面路由 `/` 和 API 路由 `/api/*` 混在同一文件。

## 服务门面层

### `novel_system/service.py`

- 入口：`NovelSystemService`、`create_service()`。
- 依赖：`AppConfig`、`Scope`、`CanonUpdateRequest`、`TimelineEvent`、`scope_filter`、`services/*` Mixin。
- 被调用方：`api.py` 通过 `create_service()` 创建服务实例。
- 调用谁：自身方法会通过 Mixin 和 `NovelSystemBase` 初始化出的依赖访问 repo、planner、retriever、validator、LLM、stats 等。
- 当前职责：组合问答、续写、索引、统计能力，提供统一服务门面；还包含 `get_canon()`、`update_canon()`、`get_timeline()`、`get_reader_payload()`。
- 边界不清：`create_service()` 实际返回 `GraphService()`；`GraphService` 覆盖了 `get_canon()`、`update_canon()`、`get_timeline()`，因此 `service.py` 中同名方法在当前实例下可能不会被调用。

### `novel_system/services/base.py`

- 入口：`NovelSystemBase.__init__()`。
- 依赖：`AppConfig`、`BookIndexRepository`、`MiniMaxClient`、`create_embedding_provider()`、`RuleBasedPlanner`、`QueryRewriter`、`SemanticScorer`、`create_reranker()`、`EvidenceGate`、`AnswerValidator`、`ContinuationValidator`、`SpoilerGuard`、`NovelConfig`。
- 被调用方：`NovelSystemService` 多重继承时初始化。
- 调用谁：初始化所有核心组件，并调用 `bootstrap_default_book()` 确保默认书籍 manifest。
- 当前职责：依赖装配、会话记忆、token 用量、默认书籍 bootstrap、通用辅助方法。
- 边界不清：依赖都在基类内部直接构造，测试和替换实现时注入边界较弱。

### `novel_system/services/qa.py`

- 入口：`QAServiceMixin.ask()`。
- 依赖：`planner`、`query_rewriter`、`HybridRetriever`、`EvidenceGate`、`AnswerValidator`、`MiniMaxClient`、`TraceLogger`、`models.py` 中的 trace/response 模型。
- 被调用方：`api.py` 的 `POST /api/books/{book_id}/ask`。
- 调用谁：加载书籍索引，规划查询，重写查询，检索证据，验证证据门槛，调用 LLM 生成答案，写 trace，记录 token。
- 当前职责：证据问答主流程。
- 边界不清：问答流程、检索合并、fallback 答案、版权拒答、scope guard、trace 组装都集中在一个 Mixin 中，职责偏宽。

### `novel_system/services/continuation.py`

- 入口：`ContinuationServiceMixin.continue_story()`。
- 依赖：`QueryRewriter`、`HybridRetriever` 的 `RetrievalHit` 类型、`ContinuationValidator`、`SpoilerGuard`、`MiniMaxClient`、`NovelConfig`、`TraceLogger`。
- 被调用方：`api.py` 的 `POST /api/books/{book_id}/continue`。
- 调用谁：加载索引，构造上下文和文风样本，调用 LLM 续写，进行一致性验证（已移除剧透判定），写 continuation trace。
- 当前职责：受约束续写主流程（不再进行剧透限制）。
- 边界不清：续写 prompt、fallback、领域规则、验证和 trace 组装集中在同一文件。

### `novel_system/services/indexing.py`

- 入口：`list_books()`、`start_book_index()`、`index_book()`、`index_default_book()`、`delete_book()`、`ensure_indexed()`。
- 依赖：`BookIndexRepository`、`BookInfo`、`Path`、后台线程。
- 被调用方：书籍列表、注册、索引、删除、状态、artifact API。
- 调用谁：`repo.ensure_book_manifest()`、`repo.build_from_txt()`、`repo.load()`、`repo.remove_book()` 等。
- 当前职责：书籍导入、异步索引状态、索引构建入口和删除保护。
- 边界不清：服务层直接操作索引状态和线程，和 repository 的职责边界待确认。

### `novel_system/services/stats.py`

- 入口：`get_storage_stats()`、`get_token_stats()`、`get_book_artifact_catalog()`、`get_book_artifact()`、`get_dashboard_data()`。
- 依赖：`AppConfig`、`EvaluationDashboardData`、artifact 文件。
- 被调用方：`/api/storage-stats`、`/api/token-stats`、`/api/dashboard`、artifact API。
- 当前职责：存储统计、token 统计、artifact 查询、Dashboard 评测数据聚合。
- 边界不清：Dashboard 评测数据是否仍依赖已清理的 `data/eval_full/` 待确认。

## 索引与产物层

### `novel_system/indexing.py`

- 入口：`BookIndexRepository`、`LoadedBookIndex`、`scope_filter()`、顶层 `build_chapter_chunks()`、`build_event_timeline()`、`build_character_cards()`、`build_book_artifacts()`。
- 依赖：`AppConfig`、`EmbeddingProvider`、`MiniMaxClient`、`vector_store`、`graph_name_policy`、`utils/text_utils.py`、`extraction_models.py`、`jieba`、`sklearn`、`networkx`、`pickle/json` 文件产物。
- 被调用方：`NovelSystemBase` 创建 `BookIndexRepository`；`IndexingServiceMixin` 调用索引构建；`GraphService` 使用 `scope_filter()`；测试覆盖索引流水线、场景、人物注册表、artifact。
- 调用谁：本地 embedding、FAISS 向量索引、LLM 结构化提取、名称过滤、文本工具。
- 当前职责：书籍 manifest、章节解析、chunk 构建、摘要、事件时间线、人物卡、人物注册表、关系图、世界规则、canon memory、文风样本、近期剧情、TF-IDF、FAISS、artifact 保存和加载。
- 边界不清：文件约 1700 行，职责过重；`BookIndexRepository._build_*` 与顶层 `build_*` 函数并存；`BookIndexRepository._extract_person_names` 与 `SceneSegmentBuilder._extract_person_names` 重复；`BookIndexRepository` 内部懒加载 `MiniMaxClient`，与服务基类中的 LLM 实例独立。

## 检索层

### `novel_system/retrieval.py`

- 入口：`RetrievalHit`、`HybridRetriever.retrieve()`。
- 依赖：`SearchOrchestrator`、`BaseReranker`。
- 被调用方：`services/qa.py` 直接导入 `HybridRetriever` 和 `RetrievalHit`；`services/continuation.py` 使用 `RetrievalHit` 类型；部分测试仍直接使用 `HybridRetriever` 或 `RetrievalHit`。
- 调用谁：`SearchOrchestrator.retrieve()`，可选调用 `reranker.rerank()`。
- 当前职责：兼容旧接口，将新检索结果包装为旧 `RetrievalHit`。
- 边界不清：这是 legacy facade，但仍在当前运行链路内，不能直接删除。

### `novel_system/search/`

- 入口：`SearchOrchestrator`、`Hit`、`reciprocal_rank_fusion()`、`SearchProfile`。
- 依赖：`search/profiles.py`、向量索引、TF-IDF payload、可选 query embedding、GraphRAG 相关语料。
- 被调用方：`retrieval.py` 和多个搜索相关测试。
- 调用谁：从 `LoadedBookIndex` 的 corpora、vector payload、vector stores 中检索和融合结果。
- 当前职责：精确人物匹配、TF-IDF 稀疏检索、dense 向量检索、GraphRAG、RRF 融合、关键词加权、scope 过滤、去重。
- 边界不清：真实检索逻辑集中在 orchestrator，未来若移除 `retrieval.py` 需要先迁移服务层类型和测试。

## Planner 与查询重写

### `novel_system/planner.py`

- 入口：`RuleBasedPlanner.plan()`、`RuleBasedPlanner.infer_memory()`、`QueryRewriter.rewrite()`、`MemoryState`、`RewrittenQuery`。
- 依赖：`models.py` 中的 `ConversationTurn`、`PlannerOutput`、`QueryIntent`、`Scope`。
- 被调用方：`services/base.py` 初始化；`services/qa.py` 和 `services/continuation.py` 在主流程中调用。
- 调用谁：主要是本文件内规则、别名扩展和历史会话解析。
- 当前职责：识别查询意图、任务类型、检索目标、scope/memory 偏好；对用户查询做别名和上下文重写。
- 边界不清：`ALIAS_EXPANSIONS` 与 `graph_name_policy.py` 的名称/别名策略可能重复，待确认统一来源。

## 验证和追踪

### `novel_system/validator.py`

- 入口：`EvidenceGate.evaluate()`、`AnswerValidator.validate()`、`ContinuationValidator.validate()`、`SpoilerGuard.detect_spoiler()`、`get_refusal_answer()`。
- 依赖：`models.py`、`entity_extractor.py`、`semantic_scorer.py`、正则和规则配置。
- 被调用方：`services/base.py` 初始化；`services/qa.py` 使用 EvidenceGate/AnswerValidator；`services/continuation.py` 使用 ContinuationValidator/SpoilerGuard。
- 调用谁：实体提取、语义评分和内部规则。
- 当前职责：证据门槛、答案 groundedness、实体一致性、续写人物/世界/文风一致性（剧透检测和内容脱敏已被服务层停用）。
- 边界不清：单文件超过 800 行且包含多个验证组件；是否拆分为 QA 验证、续写验证、剧透防护待确认。

### `novel_system/tracing.py`

- 入口：`TraceLogger.generate_trace_id()`、`trace_logger.log_ask_trace()`、`trace_logger.log_continuation_trace()`。
- 依赖：`models.py` 中的 `AskTrace`、`ContinuationTrace`，以及标准 logging/json。
- 被调用方：`services/qa.py` 和 `services/continuation.py`。
- 当前职责：把问答和续写的结构化 trace 写入日志。
- 边界不清：trace 是否需要独立持久化文件、是否只靠 logger 输出，待确认。

## LLM 层

### `novel_system/llm.py`

- 入口：`MiniMaxDirectClient`、`MimoClient`、`MiniMaxClient`、`LLMResponse`。
- 依赖：`AppConfig`、`requests`、全局限频 `_throttle()`。
- 被调用方：`NovelSystemBase` 初始化 `self.llm`；`BookIndexRepository.llm` 懒加载独立 LLM；QA/续写调用生成答案；索引构建调用结构化提取和名称过滤。
- 调用谁：MiniMax API 和 Mimo API。
- 当前职责：MiniMax 直连、Mimo fallback、统一 chat 接口、token usage 提取、think 标签清理。
- 边界不清：`MiniMaxClient` 实际是路由器，命名易与 `MiniMaxDirectClient` 混淆；LLM 实例在 service 和 repository 两处创建，生命周期不统一。

## 图谱层

### `novel_system/graph_service.py`

- 入口：`GraphService`、`get_interactive_graph()`，以及覆盖的 `get_canon()`、`update_canon()`、`get_timeline()`。
- 依赖：`NovelSystemService`、`Scope`、`TimelineEvent`、`CanonUpdateRequest`、`scope_filter`、图谱 artifact、`graph_name_policy.py`。
- 被调用方：`create_service()` 返回实例；API 的 graph/canon/timeline/reader 间接使用。
- 调用谁：索引仓库、图谱名称规范化、人物/事件语料、用户 canon 文件。
- 当前职责：交互式人物关系图、中心人物/章节范围过滤、密度预算、人物 tier、事件关联、canon/timeline 扩展。
- 边界不清：继承服务门面并覆盖同名方法，使 service 与 graph 的层级关系不清；图谱名称策略与 planner 别名策略重复，待确认。

### `novel_system/graph_name_policy.py`

- 入口：名称规范化和 GraphProfile 相关函数/模型。
- 依赖：正则、图谱 profile JSON。
- 被调用方：`indexing.py` 和 `graph_service.py`。
- 当前职责：图谱人物名清洗、别名合并、噪声过滤、profile 策略。
- 边界不清：与 `planner.py` 的硬编码别名扩展是否应合并，待确认。

## 模块边界不清汇总

| 问题 | 涉及模块 | 当前判断 |
|---|---|---|
| 服务实例真实类型不直观 | `service.py`, `graph_service.py` | `create_service()` 返回 `GraphService()`，不是纯 `NovelSystemService` |
| 同名方法覆盖 | `service.py`, `graph_service.py` | `get_canon`、`update_canon`、`get_timeline` 两处实现，当前实例走 GraphService |

| 人名/别名策略分散 | `indexing.py`, `planner.py`, `graph_name_policy.py` | 人名提取和别名扩展存在多处实现，待确认统一策略 |

| LLM 生命周期不统一 | `services/base.py`, `indexing.py`, `llm.py` | service 和 repository 都会创建 LLM 客户端 |
| 启动命令不一致 | `start_server.py`, `novel_system/api.py`, `AGENTS.md`, `docs/02` | `start_server.py` 可启动；`python -m novel_system.api` 是否可启动待确认 |
| 前端文件过大 | `static/app.js`, `templates/dashboard.html` | 当前可用但职责集中，后续可模块化 |
