# 11 AI 开发工作流规范

> 版本：1.0 | 创建日期：2026-05-23
> 本文档规定每类开发任务的标准流程，AI 必须按流程执行，不得跳步。

---

## 总原则

- **先计划，后执行**：任何任务都必须先输出修改声明，用户确认后再动手
- **小步修改**：每次只改一件事，改完验证，再改下一件
- **改完更新文档**：代码改完当次必须同步更新相关 docs/，不得拖延
- **变更必须登记**：每次改动都要在 `docs/09_变更记录.md` 追加条目

---

## 流程一：新需求处理

适用场景：用户提出新功能、新接口、新页面元素。

```
步骤 1 — 需求澄清
  阅读 docs/00_项目总览.md、docs/03_核心模块说明.md
  如果需求描述不完整，先提问，不得自行假设
  输出：需求理解确认（一句话 + 验收标准）

步骤 2 — 影响分析
  列出涉及的文件（精确到文件名）
  列出不会触碰的文件
  评估是否需要新建文件（默认不新建）
  输出：修改声明（见 AGENTS.md 第二节格式）

步骤 3 — 用户确认
  等待用户确认修改声明，未确认不得写代码

步骤 4 — 实现（小步）
  每次只改一个文件
  单次输出不超过 150 行代码
  改完一个文件后停下，等用户确认再继续

步骤 5 — 测试
  运行：conda run -n chaishu python -m pytest
  提供实际命令输出，不得凭感觉声称"应该没问题"

步骤 6 — 文档同步
  更新涉及的 docs/ 文件（路由表、模块说明等）
  在 docs/09_变更记录.md 追加变更条目
```

## 流程二：Bug 修复

适用场景：测试失败、功能异常、接口报错。

```
步骤 1 — 复现确认
  先调用 systematic-debugging skill
  确认复现步骤：什么操作、什么输入、什么错误信息
  不得在未复现的情况下猜测原因

步骤 2 — 根因定位
  阅读报错的完整 traceback
  定位到具体文件和行号
  说明根本原因（不是表面现象）
  输出：根因分析（文件:行号 + 一句话原因）

步骤 3 — 最小修复方案
  只修改导致 Bug 的代码，不做任何顺手优化
  输出修改声明，说明改了什么、为什么这样改

步骤 4 — 用户确认
  等待用户确认修复方案

步骤 5 — 实施修复
  修改代码，单次不超过 150 行

步骤 6 — 回归验证
  运行全量测试：conda run -n chaishu python -m pytest
  提供实际输出，确认无新增失败

步骤 7 — 记录
  在 docs/09_变更记录.md 追加 fix 类型条目
  说明根因和修复方案，防止同类问题复现
```

## 流程三：文件清理

适用场景：删除冗余文件、清理根目录临时文件。

```
步骤 1 — 审计确认
  阅读 docs/04_文件用途审计表.md
  阅读 docs/05_疑似冗余文件清单.md
  确认目标文件已被标记为"可删除"

步骤 2 — 引用检查
  对目标文件执行全项目 grep，确认无任何 import 或引用
  输出：grep 命令和结果

步骤 3 — 逐文件确认
  每次只提议删除 1 个文件
  输出：文件路径 + 删除理由 + grep 确认结果
  等待用户明确确认

步骤 4 — 执行删除
  用户确认后删除该文件

步骤 5 — 文档同步
  更新 docs/01_目录结构说明.md，将该文件标记为已删除
  在 docs/09_变更记录.md 追加 delete 类型条目

步骤 6 — 测试
  运行 conda run -n chaishu python -m pytest，确认删除未破坏任何功能
```

## 流程四：页面改造

适用场景：修改 `templates/dashboard.html` 或 `static/app.js` 或 `static/styles.css`。

```
步骤 1 — 现状理解
  阅读 docs/00_项目总览.md 了解前端架构（Jinja2 + 原生 JS，无框架）
  阅读目标文件，理解现有结构

步骤 2 — 改动范围声明
  说明要改哪个区域（HTML 节点 ID / JS 函数名 / CSS 类名）
  说明不会触碰的区域
  输出修改声明

步骤 3 — 用户确认

步骤 4 — 实施（小步）
  HTML/CSS/JS 分开改，每次只改一类
  保持现有 UI 风格（配色、间距、交互模式）
  不引入任何新的 JS 库或 CSS 框架

步骤 5 — 验证
  说明如何在浏览器中验证改动（访问哪个路由、触发什么操作）
  如果无法自动验证，明确告知用户需要手动验证的步骤

步骤 6 — 文档同步
  如果改动影响了 API 调用方式，更新 docs/02_技术栈与启动流程.md
  在 docs/09_变更记录.md 追加条目
```

## 流程五：组件新增（Python 模块内新增类或函数）

适用场景：在现有 `.py` 文件中新增类、函数、方法。

```
步骤 1 — 定位归属
  阅读 docs/03_核心模块说明.md，确认新功能属于哪个现有模块
  如果不确定，先提问，不得自行决定放在哪里

步骤 2 — 接口设计
  说明新函数/类的签名（参数、返回值、类型）
  说明它与现有代码的关系（调用谁、被谁调用）
  输出修改声明

步骤 3 — 用户确认

步骤 4 — 先写测试（TDD）
  调用 test-driven-development skill
  在 tests/ 下新增或修改对应测试文件
  先让测试失败，再写实现

步骤 5 — 实现
  在目标文件中添加代码
  单次不超过 150 行

步骤 6 — 验证
  运行相关测试：conda run -n chaishu python -m pytest tests/test_<模块名>.py -v
  运行全量测试：conda run -n chaishu python -m pytest

步骤 7 — 文档同步
  更新 docs/03_核心模块说明.md 中对应模块的说明
  在 docs/09_变更记录.md 追加 feat 条目
```

## 流程六：接口变更

适用场景：新增、修改、删除 `novel_system/api.py` 中的路由。

```
步骤 1 — 现状确认
  阅读 docs/02_技术栈与启动流程.md 中的路由表（18 个路由）
  阅读 novel_system/api.py 中的目标路由代码

步骤 2 — 变更声明
  说明变更的路由路径、HTTP 方法、请求/响应结构变化
  说明是否影响前端 static/app.js 中的 API 调用
  输出修改声明

步骤 3 — 用户确认

步骤 4 — 实施
  修改 api.py 中的路由
  如果影响前端，同步修改 static/app.js 中的对应调用

步骤 5 — 验证
  运行全量测试：conda run -n chaishu python -m pytest
  如果有对应的接口测试，单独运行确认

步骤 6 — 文档同步（必须）
  更新 docs/02_技术栈与启动流程.md 中的路由表
  如果请求/响应结构变化，更新 docs/03_核心模块说明.md
  在 docs/09_变更记录.md 追加条目
```

## 流程七：文档更新

适用场景：单独更新 docs/ 下的文档（不涉及代码改动）。

```
步骤 1 — 确认更新范围
  说明要更新哪个文档的哪个章节
  说明更新原因（代码已改但文档未同步 / 信息过时 / 新增说明）

步骤 2 — 实施更新
  只修改需要更新的部分，不重写整个文档
  保持文档现有格式和风格

步骤 3 — 登记
  在 docs/09_变更记录.md 追加 docs 类型条目
  说明更新了什么、为什么更新
```
