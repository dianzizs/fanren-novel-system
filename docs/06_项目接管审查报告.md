# 06 项目接管审查报告

> 生成日期：2026-05-25
> 审查范围：GraphRAG 架构迁移后全项目审计。

## 一、项目现状判断

### 1. 架构核心已完成迁移

项目已成功从传统的“混合检索 + 人工补丁”架构迁移至 **Microsoft GraphRAG (v3.0.9)** 体系。

- **主流程变迁**: `api.py` -> `services/qa.py` (async) -> `graphrag_query_engine`。
- **知识表示**: 从 `chapter_chunks.json` 等散落文件转向 GraphRAG 的 Parquet 结构化知识表（entities, relationships, communities）。
- **去重与精简**: 物理删除了 `novel_system/legacy/` 和 `tests/legacy/`，消除了大量技术债。

### 2. 核心模块稳定性

| 模块/目录 | 状态 | 评价 |
|---|---|---|
| `novel_system/graphrag_app/` | **新增/核心** | 结构清晰，通过 Python API 和 CLI 两种方式完美适配 GraphRAG。 |
| `novel_system/indexing/` | **重构完成** | 已从单文件拆分为功能明确的子包，解决了职责过重的问题。 |
| `novel_system/services/qa.py` | **已适配** | 已全面转为异步，并集成了 Local/Global/DRIFT/Basic 四种查询模式。 |
| `novel_system/services/continuation.py` | **降级中** | 当前仅提供 GraphRAG 迁移提示，待后续恢复。 |
| `tests/graphrag_app/` | **新增测试** | 建立了针对 GraphRAG 契约、表加载和投影的专项测试体系。 |

## 二、审计发现与处理建议

### 1. 遗留兼容层处理

- **`retrieval.py`**: 仍保留了 `RetrievalHit` 等类型定义以兼容部分 legacy trace 模型，但核心逻辑已不再使用。
  - **建议**: 在下一轮模型重构中彻底移除。

### 2. 验证层 (Validator) 滞后

- **`validator.py`**: 内部的 `EvidenceGate` 仍部分依赖旧的语义评分逻辑。
  - **建议**: 将验证逻辑迁移到 GraphRAG 的“响应一致性”和“事实核查”维度，利用 `community_reports` 做二次校验。

### 3. 前端耦合度与遗留 app.js

- **前端模块化已完成**：主页已升级为基于 ESM 的模块化结构（见 `static/js/main.js`），彻底解决了单文件过重的问题。
- **`static/app.js` 遗留风险**：虽然主页面已不加载该文件，但测试用例 `test_dashboard_graph_density.py` 仍对其进行内容校验。
  - **建议**：尽快重写该测试，使其指向 `static/js/graph.js` 和 `static/js/main.js`，然后彻底删除遗留的 `static/app.js`。

## 三、接管总结与后续计划

### 1. 现状结论
项目目前处于 **GraphRAG 架构稳定期**。核心问答和索引流水线已跑通，且通过了全量 181 个测试用例。文档体系（00-06）已同步更新，与代码现状一致。

### 2. 后续优先级
1. **恢复续写功能**: 利用 GraphRAG 的 `Basic Search` 提取原文文风，结合 `Local Search` 提取剧情上下文。
2. **优化索引成本**: 研究 GraphRAG 的 `incremental indexing` 或 `cache` 机制，减少 LLM 调用成本。
3. **数据清理**: 物理删除 `data/vectors/` 下的旧 FAISS 索引。
